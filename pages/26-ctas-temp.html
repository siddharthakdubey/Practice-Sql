CTAS and temp tables

Save a query's result into a real table: permanent (CTAS) or temporary (#temp). Materialise once, reuse many times.

After this topic you will create tables from a query (SELECT INTO), use local and global temp tables and table variables, index a temp table, and choose between them.

CTAS: Create Table As Select

Standard name CTAS (CREATE TABLE x AS SELECT ... in Oracle, PostgreSQL, MySQL, Snowflake). In SQL Server the same idea is written SELECT ... INTO:

SELECT OrderID, CustomerID, Sales
INTO   dbo.DeliveredOrders_Snapshot          -- creates the table AND fills it
FROM   Orders
WHERE  OrderStatus = 'Delivered';

SELECT * FROM dbo.DeliveredOrders_Snapshot;   -- 6 rows, a frozen copy
  • Column names and data types are copied from the query. NOT NULL carries over; keys, indexes, defaults and constraints do not: add them afterwards with ALTER TABLE.
  • It is a snapshot: later changes to Orders do not appear (the opposite of a view).
  • Fails if the table already exists. Use DROP TABLE IF EXISTS first.
  • Fast: minimally logged, so it is the standard way to copy big data.
-- copy just the structure, no rows
SELECT * INTO dbo.Orders_Archive FROM Orders WHERE 1 = 0;          -- condition never true

-- load more rows later into the existing table
INSERT INTO dbo.Orders_Archive SELECT * FROM Orders WHERE OrderDate < '2025-02-01';

-- quick backup before a risky change
SELECT * INTO dbo.Customers_BAK_20261101 FROM Customers;
CTAS vs INSERT ... SELECTCTAS creates the table too. INSERT...SELECT needs the table to exist (full control over types and constraints, and good for repeated loads).

Temporary tables

A table that lives in tempdb and disappears automatically. Name it with #.

-- 1) fill it from a query
SELECT CustomerID, SUM(Sales) AS Total
INTO   #CustTotals
FROM   Orders
GROUP BY CustomerID;

-- 2) reuse it as often as you like in this session
SELECT * FROM #CustTotals WHERE Total > 60;
SELECT AVG(Total) FROM #CustTotals;
UPDATE #CustTotals SET Total = 0 WHERE CustomerID = 6;           -- you can change it, unlike a CTE

-- 3) tidy up (optional, it vanishes anyway)
DROP TABLE IF EXISTS #CustTotals;

Define first, fill later (more control)

CREATE TABLE #Stage (
    OrderID INT PRIMARY KEY,
    Sales   DECIMAL(10,2),
    Flag    VARCHAR(10)
);
INSERT INTO #Stage (OrderID, Sales) SELECT OrderID, Sales FROM Orders WHERE Sales > 30;
UPDATE #Stage SET Flag = 'BIG' WHERE Sales >= 50;
CREATE INDEX ix_stage_flag ON #Stage (Flag);          -- a temp table can be indexed

Table variable

DECLARE @Top TABLE (CustomerID INT, Total DECIMAL(10,2));
INSERT INTO @Top SELECT TOP 3 CustomerID, SUM(Sales) FROM Orders GROUP BY CustomerID ORDER BY SUM(Sales) DESC;
SELECT * FROM @Top;

Why use a temp table?

  1. Break a monster query into steps you can check one at a time, with real data to inspect.
  2. Compute once, use many times: a CTE may be recalculated at every reference; a temp table is calculated once.
  3. Help the optimizer: a temp table has statistics, so joins after it get better row estimates than after a complicated nested query.
  4. Stage data in ETL: load raw rows, clean in place, then insert into the final table.
  5. Hold a working set for a procedure (topic 28) while it loops or branches.

Cautions

  • Temp tables use tempdb (shared by everyone): huge ones can fill the disk or cause contention.
  • A temp table with the same name in the same session fails on re-run: start scripts with DROP TABLE IF EXISTS #t;.
  • SELECT INTO creates a table with the types the query happens to produce, e.g. Total may become DECIMAL(38,2). Cast to what you want.
  • Permanent CTAS tables become stale snapshots. Name them with a date or a purpose, and schedule clean-up.
