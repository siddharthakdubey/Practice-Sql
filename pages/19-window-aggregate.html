Window aggregate

COUNT, SUM, AVG, MIN, MAX as window functions: totals beside each row, running totals, and moving averages with frames.

After this topic you will compute totals, averages and counts per row, build running totals and moving averages, control the frame with ROWS BETWEEN, and avoid the RANGE-default trap with ties.

Aggregate beside the detail

SELECT OrderID, CustomerID, Sales,
       COUNT(*)    OVER ()                         AS TotalOrders,     -- 10
       SUM(Sales)  OVER ()                         AS TotalSales,      -- 400
       AVG(Sales)  OVER ()                         AS AvgSales,        -- 40
       MAX(Sales)  OVER ()                         AS MaxSales,        -- 90
       SUM(Sales)  OVER (PARTITION BY CustomerID)  AS CustomerTotal
FROM Orders;

Same functions as topic 17, but every row keeps its identity. NULLs are ignored, same as before.

Typical uses

-- 1. Share of total
SELECT OrderID, Sales, ROUND(100.0 * Sales / SUM(Sales) OVER (), 1) AS PctOfTotal FROM Orders;

-- 2. Compare with average (find above-average orders, no subquery in WHERE needed)
SELECT * FROM (
    SELECT OrderID, Sales, AVG(Sales) OVER () AS AvgSales FROM Orders
) t WHERE Sales > AvgSales;                       -- 1002 (60), 1004 (90), 1008 (50), 1010 (45)

-- 3. Deviation from the group's best
SELECT OrderID, CustomerID, Sales,
       MAX(Sales) OVER (PARTITION BY CustomerID) - Sales AS GapToBest
FROM Orders;

-- 4. Spot duplicates
SELECT *, COUNT(*) OVER (PARTITION BY CustomerID, ProductID) AS TimesBought FROM Orders;

ORDER BY inside OVER: running totals

Add ORDER BY and the aggregate becomes cumulative: each row sees the rows from the start up to itself.

SELECT OrderID, OrderDate, Sales,
       SUM(Sales) OVER (ORDER BY OrderDate, OrderID) AS RunningTotal
FROM Orders;
OrderID | OrderDate | Sales | RunningTotal 1001 | 2025-01-01 | 20 | 20 1002 | 2025-01-05 | 60 | 80 1003 | 2025-01-10 | 10 | 90 1004 | 2025-01-20 | 90 | 180 1005 | 2025-02-01 | 40 | 220 1006 | 2025-02-05 | 25 | 245 1007 | 2025-02-15 | 40 | 285 1008 | 2025-03-01 | 50 | 335 1009 | 2025-03-10 | 20 | 355 1010 | 2025-03-15 | 45 | 400

Restart the total per customer with PARTITION BY:

SELECT OrderID, CustomerID, Sales,
       SUM(Sales) OVER (PARTITION BY CustomerID ORDER BY OrderDate, OrderID) AS CustomerRunning
FROM Orders WHERE CustomerID = 2;
OrderID | CustomerID | Sales | CustomerRunning 1001 | 2 | 20 | 20 1006 | 2 | 25 | 45 1009 | 2 | 20 | 65

The frame: which neighbours count?

The frame is the slice of the partition used for the current row. Syntax:

ROWS BETWEEN <start> AND <end>
-- bounds:  UNBOUNDED PRECEDING | n PRECEDING | CURRENT ROW | n FOLLOWING | UNBOUNDED FOLLOWING
FrameMeaning
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROWfrom the first row to now (running total)
ROWS BETWEEN 2 PRECEDING AND CURRENT ROWthis row and the 2 before it (3-row moving window)
ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWINGcentered: previous, current, next
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWINGnow to the end (remaining total)
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWINGthe whole partition

Moving average and running total, side by side

SELECT OrderID, Sales,
       SUM(Sales) OVER (ORDER BY OrderDate, OrderID)                              AS RunningTotal,
       AVG(Sales) OVER (ORDER BY OrderDate, OrderID
                        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)                 AS MovingAvg3
FROM Orders;
Use Moving averages smooth noisy daily numbers; running totals give "year to date"; CURRENT ROW AND UNBOUNDED FOLLOWING gives "remaining balance".

The default-frame trap: RANGE and ties

If you write ORDER BY but no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE treats rows with the same ORDER BY value (peers) as the current row together. ROWS counts physical rows.

SELECT FirstName, Salary,
       SUM(Salary) OVER (ORDER BY Salary)                                       AS DefaultRange,
       SUM(Salary) OVER (ORDER BY Salary ROWS UNBOUNDED PRECEDING)             AS RowsRunning
FROM Employees;
FirstName | Salary | DefaultRange | RowsRunning Frank | 55000 | 110000 | 55000 Carol | 55000 | 110000 | 110000 Kevin | 65000 | 175000 | 175000 Mary | 75000 | 250000 | 250000 Michael | 90000 | 340000 | 340000
Always write ROWS for running totalsThe default RANGE gives both tied rows the same (full) total and is also slower in SQL Server (it spills to disk). With ROWS and an ORDER BY that is unique (add a tie-breaker such as the primary key) the result is exact and repeatable. Row 2 above (55000 vs 110000) depends on which tied row is read first unless you add a tie-breaker.

Pitfalls

  • Forgetting that OVER (ORDER BY ...) changes meaning: SUM(x) OVER () is a grand total, SUM(x) OVER (ORDER BY y) is a running total.
  • Integer maths: AVG(int) OVER () truncates. Multiply by 1.0.
  • Frames only apply with ORDER BY (and not to ranking functions, which ignore them).
  • Window aggregates cannot use DISTINCT in SQL Server (COUNT(DISTINCT x) OVER fails). Workaround: dense-rank trick or a pre-aggregation CTE.
