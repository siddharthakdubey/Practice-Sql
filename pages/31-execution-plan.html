Execution plan

The engine's step-by-step recipe for your query. Learn to read it, and you can see why a query is slow instead of guessing.

After this topic you will open estimated and actual plans, read operators and arrows, tell scan from seek, know the three join algorithms (nested loops, hash, merge), spot red flags (key lookups, spills, bad estimates, implicit conversions) and use SET STATISTICS IO/TIME.

What it is

SQL is declarative: you say what. The optimizer compares many possible strategies using row-count statistics and picks the cheapest. The result is the execution plan: a tree of operators, each taking rows in and passing rows out (just like the "pipeline of tables" from topic 1).

SELECT c.FirstName, SUM(o.Sales) AS Total
FROM   Customers c JOIN Orders o ON o.CustomerID = c.CustomerID
WHERE  o.OrderStatus = 'Delivered'
GROUP BY c.FirstName;

In the Messages tab you get e.g. Table 'Orders'. Scan count 1, logical reads 2. Logical reads (8 KB pages touched) is the most reliable metric for comparing two versions of a query: it does not depend on caching or other users.

Reading a plan

  • Read right to left and top to bottom: data flows from the right-hand leaf operators (table access) to the left, ending at SELECT.
  • Arrow thickness = number of rows passed. A fat arrow early followed by a filter late means work was wasted.
  • Cost % on each operator is its share of the estimated total. Start with the most expensive one.
  • Hover an operator: estimated vs actual rows, I/O, CPU, which index, predicate used.
  • Yellow triangle = warning (spill, missing statistics, implicit conversion). Green text at the top = missing index suggestion.

The same plan for the query above, drawn as a tree (right to left it flows upwards):

SELECT
  └─ Hash Match (Aggregate)                      GROUP BY FirstName / SUM
       └─ Hash Match (Inner Join)                join Customers + Orders
            ├─ Clustered Index Scan (Customers)  5 rows
            └─ Clustered Index Scan (Orders)     filter OrderStatus = 'Delivered'  -> 6 of 10 rows

The three join algorithms, visualised

1. Nested loops

For each row of the outer input, find the matching rows in the inner input (ideally with an index seek). It is exactly the row-by-row picture from topics 8 and 9:

2. Hash join

Build: read the smaller input and put each row into a hash table by its key. Probe: read the other input once; for every row hash its key, jump to one bucket, compare there. No sorting, no index needed.

3. Merge join

Both inputs sorted by the join key. Walk through them side by side with two pointers, like zipping: advance the pointer with the smaller key; when keys are equal, output the match. One pass over each input, almost no memory. Needs sorted data (from an index, or a Sort operator which adds cost).

A tuning routine

  1. Capture the actual plan and STATISTICS IO for a baseline.
  2. Find the costliest operator; compare estimated vs actual rows around it.
  3. Make one change (index, rewrite, statistics) and measure again: logical reads before and after.
  4. Check it still returns the same result (EXCEPT both versions: topic 10).
  5. Test on realistic data volume. A plan on 10 rows tells you nothing about 10 million.
Other toolsQuery Store (history of plans and regressions), Activity Monitor, sys.dm_exec_query_stats, and Extended Events. The same idea in other engines: EXPLAIN ANALYZE in PostgreSQL, EXPLAIN in MySQL.
