DML commands

Data Manipulation Language: INSERT, UPDATE, DELETE and MERGE change the rows inside a table.

After this topic you will add, change and remove rows safely, use INSERT ... SELECT, OUTPUT, MERGE, and wrap risky changes in a transaction you can roll back.
Practice ruleRe-run sql/00_setup.sql any time to restore the original data. In real systems there is no such button, so learn the safe habits below now.

INSERT: add rows

-- 1. name the columns (always do this), give values in the same order
INSERT INTO Customers (CustomerID, FirstName, LastName, Country, Score)
VALUES (6, 'Priya', 'Nair', 'India', 620);

-- 2. several rows in one statement (fast: one round trip)
INSERT INTO Customers (CustomerID, FirstName, Country)
VALUES (7, 'Omar', 'UAE'),
       (8, 'Lena', 'Germany');          -- LastName and Score become NULL

-- 3. rows that come from another query
INSERT INTO Customers (CustomerID, FirstName, LastName, Country, Score)
SELECT EmployeeID + 100, FirstName, LastName, 'Staff', 0
FROM Employees;
  • Columns you leave out get their DEFAULT, or NULL if allowed, or an error if they are NOT NULL with no default.
  • Without the column list (INSERT INTO Customers VALUES (...)) the order must match the table exactly. Fragile: avoid.
  • Types must be convertible; text goes in quotes, numbers do not.
  • With an IDENTITY column leave it out; SQL Server numbers it.

UPDATE: change existing rows

UPDATE Customers
SET    Score = 0
WHERE  Score IS NULL;                         -- only these rows

UPDATE Customers
SET    Score = Score + 50, Country = 'US'     -- many columns, expressions allowed
WHERE  CustomerID = 3;
The classic disaster: UPDATE without WHEREchanges every row. Habit: write the SELECT with the same WHERE first, check the rows, then turn it into an UPDATE. Also check @@ROWCOUNT afterwards.

UPDATE using another table (join)

UPDATE o
SET    o.Sales = o.Quantity * p.Price         -- recalculate Sales from the price list
FROM   Orders AS o
JOIN   Products AS p ON p.ProductID = o.ProductID
WHERE  o.OrderStatus = 'Processing';

The alias o after UPDATE says which table is changed; the FROM/JOIN supplies the values. (Join details: topic 8.)

DELETE: remove rows

DELETE FROM Customers WHERE CustomerID > 5;           -- the extra rows we added
DELETE FROM Orders  WHERE OrderStatus = 'Processing';
  • Again, no WHERE means every row goes. TRUNCATE TABLE does the same, faster (topic 5).
  • A parent row that is still referenced by a foreign key cannot be deleted: the DB protects you.
  • Many systems use soft delete (IsDeleted = 1 or a status) so history survives.

OUTPUT: see what changed

UPDATE Customers
SET    Score = Score + 10
OUTPUT deleted.CustomerID, deleted.Score AS OldScore, inserted.Score AS NewScore
WHERE  Country = 'Germany';
CustomerID | OldScore | NewScore 1 | 350 | 360 4 | 500 | 510

deleted and inserted are virtual tables holding the old and new row images. Great for audit trails and for checking your own change.

MERGE: upsert (insert or update)

MERGE Customers AS target
USING (VALUES (2, 'Kevin', 'Brown', 'USA', 950),
              (9, 'Neha',  'Rao',   'India', 400))
      AS source (CustomerID, FirstName, LastName, Country, Score)
   ON target.CustomerID = source.CustomerID
WHEN MATCHED THEN
     UPDATE SET target.Score = source.Score
WHEN NOT MATCHED BY TARGET THEN
     INSERT (CustomerID, FirstName, LastName, Country, Score)
     VALUES (source.CustomerID, source.FirstName, source.LastName, source.Country, source.Score);

Kevin (2) exists, so his score is updated; Neha (9) does not, so she is inserted. One statement, one pass. (MERGE has some known edge-case bugs in SQL Server; many teams prefer an explicit UPDATE followed by INSERT in a transaction.)

Transactions: all or nothing

BEGIN TRANSACTION;

UPDATE Accounts SET Balance = Balance - 500 WHERE AccountID = 1;   -- debit
UPDATE Accounts SET Balance = Balance + 500 WHERE AccountID = 2;   -- credit

-- looks right?
COMMIT;        -- make permanent
-- ROLLBACK;   -- or undo everything since BEGIN

A transaction follows the ACID rules:

ACID
Atomic: all steps happen or noneConsistent: constraints hold before and afterIsolated: concurrent users do not see half-done workDurable: after COMMIT it survives a crash

As a bank engineer this is your home turf: a transfer must never debit without crediting. While a transaction is open it holds locks, so keep it short and never leave one open while you go for lunch.

Safe-change pattern for production-like data:

BEGIN TRAN;
    UPDATE Customers SET Score = 0 WHERE Country = 'USA';
    SELECT @@ROWCOUNT AS RowsChanged;      -- expected 3?
    SELECT * FROM Customers;               -- eyeball it
ROLLBACK;                                   -- change to COMMIT only when happy
Try it

1) Insert yourself as customer 10. 2) Raise the Score of all USA customers by 10% (careful with NULL). 3) Wrap a DELETE of all Orders in a transaction, check the count with SELECT COUNT(*) FROM Orders, then ROLLBACK and check again. 4) Write a MERGE that updates a product price or inserts the product.
