Triggers

SQL that runs automatically when rows are inserted, updated or deleted: audit trails, rules and derived data.

After this topic you will write AFTER and INSTEAD OF triggers, use the inserted and deleted pseudo-tables, build a safe multi-row audit trigger, and know when not to use a trigger.

What is a trigger?

A special kind of stored procedure attached to a table (or a view, or the database) that SQL Server fires by itself on an event. Nobody calls it.

TypeFires onTypical use
DML trigger: AFTER (FOR)after INSERT / UPDATE / DELETE succeeded on the tableaudit log, update summary table, cross-table validation
DML trigger: INSTEAD OFreplaces the INSERT/UPDATE/DELETE with your codemake a complex view updatable, soft delete
DDL triggerCREATE / ALTER / DROPblock DROP TABLE in production, log schema changes
Logon triggera login attemptlimit sessions (rare)

The magic tables: inserted and deleted

Inside a DML trigger two virtual tables with the same columns as the base table exist:

Statementinserted holdsdeleted holds
INSERTthe new rowsempty
DELETEemptythe removed rows
UPDATEthe rows after the changethe rows before the change
One statement, many rows, one trigger runA single UPDATE ... WHERE Department='Sales' that changes 3 rows fires the trigger once, and inserted has 3 rows. Triggers must be written set-based. Writing SELECT @x = Salary FROM inserted assumes one row and silently handles only one of them: the most common trigger bug.

Example: an audit trail for salary changes

CREATE TABLE dbo.SalaryAudit (
    AuditID    INT IDENTITY(1,1) PRIMARY KEY,
    EmployeeID INT,
    OldSalary  DECIMAL(10,2),
    NewSalary  DECIMAL(10,2),
    ChangedBy  SYSNAME      DEFAULT SUSER_SNAME(),    -- who did it
    ChangedAt  DATETIME2    DEFAULT SYSUTCDATETIME()  -- when (UTC)
);
GO
CREATE OR ALTER TRIGGER dbo.trg_Employees_SalaryAudit
ON dbo.Employees
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF NOT UPDATE(Salary) RETURN;                       -- ignore updates that did not touch Salary

    INSERT INTO dbo.SalaryAudit (EmployeeID, OldSalary, NewSalary)
    SELECT d.EmployeeID, d.Salary, i.Salary
    FROM   deleted  d
    JOIN   inserted i ON i.EmployeeID = d.EmployeeID    -- match old and new version of the same row
    WHERE  ISNULL(d.Salary, -1) <> ISNULL(i.Salary, -1);  -- only real changes (NULL-safe)
END;
GO
UPDATE Employees SET Salary = Salary * 1.10 WHERE Department = 'Sales';
SELECT * FROM dbo.SalaryAudit;
AuditID | EmployeeID | OldSalary | NewSalary 1 | 3 | 75000.00 | 82500.00 2 | 4 | 90000.00 | 99000.00 3 | 5 | 55000.00 | 60500.00

(ChangedBy / ChangedAt omitted.) The trigger runs inside the same transaction as the UPDATE: if the trigger fails, or you ROLLBACK, the data change is undone as well, so the audit never disagrees with the data.

Example: a rule a CHECK cannot express (reject)

CREATE OR ALTER TRIGGER dbo.trg_Orders_NoShipBeforeOrder
ON dbo.Orders
AFTER INSERT, UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF EXISTS (SELECT 1 FROM inserted WHERE ShipDate < OrderDate)
    BEGIN
        THROW 50010, 'ShipDate cannot be earlier than OrderDate.', 1;   -- aborts the statement (rolls it back)
    END
END;

(For a rule within one table, a CHECK (ShipDate >= OrderDate) constraint is simpler and faster: prefer constraints; use triggers when other tables are involved.)

INSTEAD OF: replace the action

-- Soft delete: DELETE becomes "mark as inactive"
ALTER TABLE Customers ADD IsActive BIT NOT NULL DEFAULT 1;
GO
CREATE OR ALTER TRIGGER dbo.trg_Customers_SoftDelete
ON dbo.Customers
INSTEAD OF DELETE
AS
BEGIN
    SET NOCOUNT ON;
    UPDATE c SET IsActive = 0
    FROM dbo.Customers c JOIN deleted d ON d.CustomerID = c.CustomerID;   -- the real DELETE never happens
END;
GO
DELETE FROM Customers WHERE CustomerID = 5;      -- Anna is still there, with IsActive = 0

INSTEAD OF triggers on a view let you INSERT/UPDATE a multi-table view by hand-coding where each column goes (topic 25).

Enable, disable, drop, list

DISABLE TRIGGER dbo.trg_Employees_SalaryAudit ON dbo.Employees;     -- e.g. during a bulk load
ENABLE  TRIGGER dbo.trg_Employees_SalaryAudit ON dbo.Employees;
DROP TRIGGER IF EXISTS dbo.trg_Employees_SalaryAudit;
SELECT name, parent_class_desc, is_disabled FROM sys.triggers;       -- which triggers exist

A DDL trigger (guard rail)

CREATE TRIGGER trg_NoDropTable ON DATABASE FOR DROP_TABLE AS
BEGIN
    RAISERROR ('DROP TABLE is blocked. Disable this trigger first.', 16, 1);
    ROLLBACK;
END;

Downsides: use with care

  • Hidden behaviour: the code runs invisibly. A developer sees an UPDATE take twice as long and does not know why. Document triggers.
  • Performance: they run on every matching statement, inside the transaction, holding locks longer. Bulk loads slow down.
  • Cascades: a trigger that updates another table with its own trigger... chains and loops (recursive triggers are off by default).
  • Harder to test and debug than a procedure or application code.
  • Not fired by TRUNCATE, bulk inserts without FIRE_TRIGGERS, or if disabled.
