Advanced SQL techniques

From single queries to well-structured SQL: build answers in layers, store them, reuse them, make them fast.

After this topic you will see how the advanced topics fit together, know the "layered query" way of thinking, and have a checklist for writing readable, correct SQL for complex questions.

The big picture

A single SELECT can only do so much. Real questions ("which customers spent more than average in their first month, excluding refunds?") need several steps. The advanced toolbox gives you different ways to name and reuse those steps:

Think in layers

Do not try to write the final query in one go. Decompose the question into small steps, where each step is a table you can inspect, then stack them. Question: "Which customers have more than 50 of delivered sales, and what are their names?"

WITH delivered AS (                          -- layer 1: filter
    SELECT CustomerID, Sales FROM Orders WHERE OrderStatus = 'Delivered'
),
per_customer AS (                            -- layer 2: summarise
    SELECT CustomerID, SUM(Sales) AS Total FROM delivered GROUP BY CustomerID
),
big AS (                                     -- layer 3: filter the summary
    SELECT * FROM per_customer WHERE Total > 50
)
SELECT c.FirstName, b.Total                  -- layer 4: add names
FROM big b JOIN Customers c ON c.CustomerID = b.CustomerID;

Each CTE can be run on its own (select from it) while debugging. This is how professionals write complex SQL: small, named, testable steps.

Checklist for any complex query

  1. Grain: what does one row of my result represent (one customer? one order? one customer-month?). Write it down.
  2. Sources: which tables, and what is the key of each? Is any join one-to-many (fan-out risk)?
  3. Filters: row filters first (WHERE), group filters later (HAVING), keep NULLs in mind.
  4. Layers: aggregate at the right grain before joining to a table at a different grain.
  5. Verify: sanity-check totals against a simple query (SELECT SUM(Sales) FROM Orders), row counts before and after each join, and edge cases (NULL, ties, empty groups).
  6. Then optimise: read the execution plan, add or adjust indexes. Correct first, fast second.

Readable SQL style

-- keywords upper case, one clause per line, commas leading or trailing consistently,
-- aliases meaningful (c, o, p are fine for tiny queries; cust/ord for big ones)
SELECT  c.CustomerID,
        c.FirstName,
        SUM(o.Sales) AS TotalSales
FROM        Customers AS c
INNER JOIN  Orders    AS o  ON o.CustomerID = c.CustomerID
WHERE       o.OrderStatus = 'Delivered'
GROUP BY    c.CustomerID, c.FirstName
HAVING      SUM(o.Sales) > 50
ORDER BY    TotalSales DESC;
  • Comment the why ("excludes test accounts, per finance"), not the what.
  • Never SELECT * in production code. Always qualify columns with an alias when more than one table is involved.
  • Prefer explicit JOIN ... ON to old comma joins (FROM a, b WHERE ...).
  • Put business rules (statuses, thresholds) in one place, not repeated ten times.

Where each technique shines

  • One-off analysis: CTEs.
  • Same logic used by many queries/people: a view.
  • Heavy intermediate result reused several times in one script: a temp table (and index it).
  • Business operation with steps, parameters and permissions: stored procedure.
  • Rule that must always happen, whatever application changes the data (audit trail): trigger, used sparingly.
