Stored procedures

Save a block of SQL on the server with a name and parameters, then call it like a function: logic, transactions and error handling in one place.

After this topic you will create procedures with input/output parameters, use variables, IF, WHILE, TRY/CATCH and transactions inside them, call them with EXEC, avoid SQL injection in dynamic SQL, and know procedures vs functions vs views.

Why a stored procedure?

  • Reuse: write once, call from SSMS, an application, a scheduled job.
  • Parameters: a view cannot take them.
  • Several statements and logic: IF/ELSE, loops, transactions, error handling.
  • Security: grant EXECUTE on the procedure without giving table access. The app can only do what the procedure allows.
  • Performance: the plan is compiled and cached, and fewer round trips to the server.
  • One place to change a business rule.

Create and run

CREATE OR ALTER PROCEDURE dbo.usp_GetCustomerOrders
    @CustomerID INT                          -- input parameter
AS
BEGIN
    SET NOCOUNT ON;                          -- don't send "n rows affected" messages (less chatter, faster)

    SELECT OrderID, OrderDate, OrderStatus, Sales
    FROM   Orders
    WHERE  CustomerID = @CustomerID
    ORDER BY OrderDate;
END;
GO

EXEC dbo.usp_GetCustomerOrders @CustomerID = 2;          -- call it (name the parameter: clearer)
EXEC dbo.usp_GetCustomerOrders 2;                         -- positional also works
OrderID | OrderDate | OrderStatus | Sales 1001 | 2025-01-01 | Delivered | 20 1006 | 2025-02-05 | Delivered | 25 1009 | 2025-03-10 | Shipped | 20

usp_ is a common prefix ("user stored procedure"). Do not use sp_: SQL Server looks for those in the master database first.

Parameters: defaults and OUTPUT

CREATE OR ALTER PROCEDURE dbo.usp_CustomerSummary
    @Country    VARCHAR(50),
    @MinTotal   DECIMAL(10,2) = 0,               -- optional: default value
    @CustomerCount INT OUTPUT                    -- sends a value back to the caller
AS
BEGIN
    SET NOCOUNT ON;

    SELECT c.FirstName, SUM(o.Sales) AS Total
    FROM   Customers c
    JOIN   Orders o ON o.CustomerID = c.CustomerID
    WHERE  c.Country = @Country
    GROUP BY c.FirstName
    HAVING SUM(o.Sales) >= @MinTotal;

    SET @CustomerCount = @@ROWCOUNT;            -- rows returned by the SELECT above
END;
GO

DECLARE @n INT;
EXEC dbo.usp_CustomerSummary @Country = 'USA', @MinTotal = 60, @CustomerCount = @n OUTPUT;
SELECT @n AS HowMany;                            -- 2

Variables and control flow

DECLARE @i INT = 1, @msg VARCHAR(100);           -- variables start with @
SET @msg = 'Hello';                              -- SET or SELECT assigns
SELECT @msg = FirstName FROM Customers WHERE CustomerID = 2;    -- from a query (Kevin)

IF @i = 1
    PRINT 'one';
ELSE IF @i = 2
    PRINT 'two';
ELSE
BEGIN                                            -- BEGIN...END groups several statements
    PRINT 'something else';
    PRINT 'still in the ELSE';
END;

WHILE @i <= 3
BEGIN
    PRINT 'loop ' + CAST(@i AS VARCHAR(3));
    SET @i += 1;
END;
Set-based firstSQL is built to handle many rows in a single statement. A WHILE loop that updates one row at a time is often 100x slower than one UPDATE. Use loops for control flow (batches of work, iterating over a few items), not row-by-row data processing.

Transactions and error handling

CREATE TABLE Accounts (AccountID INT PRIMARY KEY, Owner VARCHAR(50), Balance DECIMAL(12,2) CHECK (Balance >= 0));
INSERT INTO Accounts VALUES (1, 'Asha', 1000), (2, 'Ravi', 200);
GO
CREATE OR ALTER PROCEDURE dbo.usp_Transfer
    @FromAcc INT, @ToAcc INT, @Amount DECIMAL(12,2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;                           -- any runtime error rolls back the whole transaction

    BEGIN TRY
        IF @Amount <= 0 THROW 50001, 'Amount must be positive.', 1;

        BEGIN TRAN;
            UPDATE Accounts SET Balance = Balance - @Amount WHERE AccountID = @FromAcc;   -- CHECK stops overdraft
            UPDATE Accounts SET Balance = Balance + @Amount WHERE AccountID = @ToAcc;
        COMMIT;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;             -- undo the debit if the credit failed
        THROW;                                   -- re-raise the original error to the caller
    END CATCH
END;
GO
EXEC dbo.usp_Transfer 1, 2, 300;      -- ok:  Asha 700, Ravi 500
EXEC dbo.usp_Transfer 2, 1, 9999;     -- fails (CHECK violated), nothing changes
  • TRY/CATCH: errors in TRY jump to CATCH. Inside CATCH use ERROR_MESSAGE(), ERROR_NUMBER(), ERROR_LINE().
  • THROW raises an error (or re-raises it inside CATCH).
  • Always ROLLBACK if @@TRANCOUNT > 0 in CATCH.
  • This is the classic ACID demonstration: both updates or neither (topic 6).

Dynamic SQL and injection

-- DANGEROUS: text concatenation
DECLARE @sql NVARCHAR(MAX) = N'SELECT * FROM Customers WHERE Country = ''' + @Country + '''';   -- @Country = ''' OR 1=1 --
EXEC(@sql);

-- SAFE: parameters with sp_executesql
EXEC sp_executesql
     N'SELECT * FROM Customers WHERE Country = @c',
     N'@c VARCHAR(50)',
     @c = @Country;
SQL injectionNever build SQL by pasting user input into a string. Values must travel as parameters. Identifiers (table/column names) cannot be parameters: validate them against a whitelist or use QUOTENAME().

-- an inline table-valued function = a parameterised view (fast and optimizable)
CREATE OR ALTER FUNCTION dbo.fn_OrdersOf (@CustomerID INT) RETURNS TABLE AS
RETURN SELECT OrderID, Sales FROM Orders WHERE CustomerID = @CustomerID;
GO
SELECT * FROM dbo.fn_OrdersOf(2);

Good practice

  • SET NOCOUNT ON; schema-qualify names (dbo.Orders); name parameters clearly; comment the header (purpose, author, date, change log).
  • Validate parameters; return meaningful errors with THROW.
  • Keep procedures focused (one job). Avoid SELECT *.
  • Watch parameter sniffing: the plan is built for the first parameter values and reused; a plan good for a rare value can be bad for a common one. Fixes: OPTION (RECOMPILE), OPTIMIZE FOR, better indexes (topics 30, 31).
  • Keep procedures in source control (like your Git repo) and deploy with scripts: CREATE OR ALTER makes that idempotent.

Manage them
