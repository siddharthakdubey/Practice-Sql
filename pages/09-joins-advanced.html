SQL joins (advanced)

Anti joins, CROSS and self joins, ON versus WHERE, and how to choose the right join for the question.

After this topic you will find rows with no match (anti joins), generate combinations (CROSS JOIN), join a table to itself (hierarchies), and avoid the "LEFT JOIN turned INNER" bug.

Anti joins: rows that have NO match

SQL has no ANTI JOIN keyword. You build it with a LEFT/RIGHT/FULL join and a NULL test on the other table's key. The unmatched side shows up as NULLs, so IS NULL finds exactly those rows.

Left anti join: "customers who never ordered"

SELECT c.CustomerID, c.FirstName
FROM   Customers c
LEFT JOIN Orders o ON o.CustomerID = c.CustomerID
WHERE  o.OrderID IS NULL;          -- test a column that can NEVER be NULL in a real match (the key)
CustomerID | FirstName 5 | Anna

Right anti join: "orders whose customer does not exist"

SELECT o.OrderID, o.CustomerID
FROM   Customers c
RIGHT JOIN Orders o ON o.CustomerID = c.CustomerID
WHERE  c.CustomerID IS NULL;       -- or write it as Orders o LEFT JOIN Customers c ...
OrderID | CustomerID 1004 | 6

This is a data quality check: orphan rows that a missing foreign key let through.

Full anti join: "everything that has no partner on either side"

SELECT c.CustomerID AS CustCustomerID, o.OrderID
FROM   Customers c
FULL JOIN Orders o ON o.CustomerID = c.CustomerID
WHERE  c.CustomerID IS NULL OR o.OrderID IS NULL;
Three ways to write "has no match"1) LEFT JOIN + IS NULL (above). 2) WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerID = c.CustomerID). 3) WHERE CustomerID NOT IN (SELECT CustomerID FROM Orders), which is dangerous if the subquery can return NULL. NOT EXISTS and LEFT JOIN are the safe choices and usually the fastest.

CROSS JOIN: every combination

SELECT s.Size, c.Color
FROM   (VALUES ('S'), ('M')) AS s(Size)
CROSS JOIN (VALUES ('Red'), ('Blue'), ('Green')) AS c(Color);

Rows = rows in A × rows in B. Useful for: all product-size-colour variants, a calendar of every date × every store (then LEFT JOIN actual sales to see missing days), test data. Dangerous on big tables: 1 million × 1 million = 1 trillion rows.

SELF JOIN: a table joined to itself

Employees have a ManagerID that points to another row of the same table. Treat it as two copies under different aliases.

SELECT e.FirstName AS Employee, m.FirstName AS Manager
FROM   Employees e
LEFT JOIN Employees m ON m.EmployeeID = e.ManagerID;     -- LEFT so the top boss (no manager) stays
Employee | Manager Frank | NULL Kevin | Frank Mary | Frank Michael | Kevin Carol | Mary

This handles one level. For a whole org chart of unknown depth you need a recursive CTE (topic 24).

ON vs WHERE in outer joins

For an INNER JOIN, a condition in ON or in WHERE gives the same result. For an outer join, it does not:

  • ON decides which rows match. Unmatched left rows still survive.
  • WHERE runs after the join and deletes rows, including the NULL-filled ones.
-- A: condition in ON  -> keeps all customers
SELECT c.FirstName, o.OrderID
FROM Customers c LEFT JOIN Orders o
     ON o.CustomerID = c.CustomerID AND o.OrderStatus = 'Delivered';

-- B: condition in WHERE -> Mary and Anna vanish
SELECT c.FirstName, o.OrderID
FROM Customers c LEFT JOIN Orders o ON o.CustomerID = c.CustomerID
WHERE o.OrderStatus = 'Delivered';
FirstName | OrderID Jossef | 1003 Jossef | 1008 Kevin | 1001 Kevin | 1006 Mary | NULL Mark | 1005 Mark | 1010 Anna | NULL
FirstName | OrderID Jossef | 1003 Jossef | 1008 Kevin | 1001 Kevin | 1006 Mark | 1005 Mark | 1010
Rule of thumbWith LEFT JOIN: conditions on the left table go in WHERE; conditions on the right table go in ON. Exception: the deliberate IS NULL anti-join test goes in WHERE.

Non-equi joins and more tricks

  • Range join: JOIN SalaryBands b ON e.Salary BETWEEN b.Low AND b.High: the ON is not an equality, any condition works.
  • Multi-column key: ON a.Year = b.Year AND a.Region = b.Region.
  • Alternative to FULL JOIN (not in MySQL): LEFT JOIN UNION RIGHT JOIN.
  • Join and aggregate: aggregate before joining when the other side has many rows, to avoid fan-out (topic 17, 24).

Choosing a join: decision flow

Ask yourselfUse
Do I only want rows that exist on both sides?INNER JOIN
Must every row of table A appear, match or not?A LEFT JOIN B
Do I need everything from both, to compare?FULL JOIN
Do I want A rows with no partner in B?LEFT JOIN ... WHERE B.key IS NULL, or NOT EXISTS
Do I want every combination?CROSS JOIN
Does the table reference itself?Self join (or recursive CTE for unknown depth)

1) Products that were never ordered (Socks). 2) Employees who never made a sale (Frank, Kevin). 3) Employee, manager and manager's manager in one row (join Employees three times). 4) Build a list of every (Customer, Product) pair with a CROSS JOIN, then LEFT JOIN Orders to flag pairs that actually happened.
