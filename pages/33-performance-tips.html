30 performance tips

Practical habits for fast SQL Server queries, grouped by where the time usually goes. Measure first (topic 31), then apply.

After this topic you will have a checklist of 30 concrete changes: what to write instead, and why it is faster.
First law of tuningMake it correct, then measure (SET STATISTICS IO, TIME ON, actual plan), change one thing, measure again. Most gains come from reading fewer rows and fewer pages, not from clever syntax.

A. Fetching data

1Select only the columns you need

Wide rows mean more pages and more network, and they defeat covering indexes.

-- slow:  SELECT * FROM Orders;
SELECT OrderID, Sales FROM Orders;

2Filter early and hard

Put row filters in WHERE (not HAVING) so fewer rows reach grouping and joins. Use HAVING only for aggregate conditions.

3Limit what you return

TOP n ... ORDER BY or OFFSET-FETCH for screens and previews. Do not pull a million rows to show ten.

4Avoid DISTINCT as a bandage

If DISTINCT "fixes" duplicates, a join is probably producing them. Fix the join (or use EXISTS). DISTINCT forces a sort or hash.

5UNION ALL instead of UNION

UNION removes duplicates (sort/hash). If sets cannot overlap or duplicates are fine, UNION ALL costs nothing extra.

6Use EXISTS to test existence, not COUNT

-- slow: IF (SELECT COUNT(*) FROM Orders WHERE CustomerID = 3) > 0
IF EXISTS (SELECT 1 FROM Orders WHERE CustomerID = 3)    -- stops at the first match

B. Filtering

7Keep predicates sargable

No function on the indexed column.

-- slow: WHERE YEAR(OrderDate) = 2025
WHERE OrderDate >= '2025-01-01' AND OrderDate < '2026-01-01'

8No leading wildcards

LIKE 'Ke%' can seek; LIKE '%vin' must scan. For real text search use Full-Text Search.

9Match data types

Comparing an INT column to '3', or a VARCHAR column to an NVARCHAR parameter, causes implicit conversion on the column side and kills seeks. Watch for the yellow warning in the plan.

10Avoid OR across different columns

-- may scan:  WHERE CustomerID = 3 OR ProductID = 101
SELECT ... WHERE CustomerID = 3
UNION ALL
SELECT ... WHERE ProductID = 101 AND (CustomerID <> 3 OR CustomerID IS NULL)   -- each branch can seek its own index

11Prefer NOT EXISTS over NOT IN

NOT IN is NULL-unsafe and often slower. Use NOT EXISTS or LEFT JOIN ... IS NULL.

C. Joins

12Join on indexed, same-typed columns

Foreign-key columns (Orders.CustomerID) are the most commonly missing indexes. SQL Server does not index them automatically.

13Use the join type you mean

INNER JOIN when unmatched rows are not wanted (it gives the optimizer more freedom than LEFT JOIN). Do not LEFT JOIN "just in case".

14Aggregate before joining

Summarise the big table first (CTE/derived table), then join the small summary. Avoids fan-out and joins fewer rows (topics 17, 23).

15Never join without ON

An accidental CROSS JOIN multiplies rows. Check the row count after each join.

16Do not join tables you do not use

Remove unused lookups from queries and views; every join costs, even if its columns are not selected (unless the optimizer can prove it is redundant).

D. Aggregation and window functions

17Replace correlated subqueries with a join or window function

-- row-by-row feel: (SELECT AVG(Sales) FROM Orders o2 WHERE o2.CustomerID = o.CustomerID)
AVG(Sales) OVER (PARTITION BY CustomerID)        -- one pass

18Index the columns in PARTITION BY and ORDER BY of windows

An index on (CustomerID, OrderDate) lets ROW_NUMBER() OVER (PARTITION BY CustomerID ORDER BY OrderDate) skip the Sort.

19Write ROWS, not the default RANGE, for running totals

ROWS UNBOUNDED PRECEDING is far faster than the default RANGE frame in SQL Server (topic 19).

20One pass with conditional aggregation

-- instead of three queries or three subqueries:
SELECT SUM(CASE WHEN OrderStatus='Delivered' THEN Sales END) AS Delivered,
       SUM(CASE WHEN OrderStatus='Shipped'   THEN Sales END) AS Shipped
FROM Orders;

E. Writing data

21Set-based, not row-by-row

One UPDATE ... WHERE beats a cursor or WHILE loop updating one row at a time by orders of magnitude.

22Batch large changes

Deleting or updating millions of rows in one statement bloats the log and locks the table. Do it in chunks:

WHILE 1 = 1
BEGIN
    DELETE TOP (10000) FROM Logs WHERE CreatedAt < '2025-01-01';
    IF @@ROWCOUNT = 0 BREAK;
END;

23Insert many rows per statement

One INSERT ... VALUES (..),(..),(..) or INSERT ... SELECT instead of thousands of single-row inserts. For huge loads use BULK INSERT / bcp / minimal logging.

24Keep transactions short

Locks are held until COMMIT. Do reads and calculations first, then open the transaction for the quick writes; never wait for user input inside one.

25TRUNCATE instead of DELETE for whole tables

Deallocates pages, minimal logging (topic 5).

F. Indexing, design and tooling

26Index what you filter, join, group and order by, and no more

Create covering indexes for hot queries with INCLUDE. Drop unused and duplicate indexes: each one slows every write (topic 30).

27Choose the right data types

Smallest type that fits (INT not BIGINT, DATE not DATETIME, VARCHAR not NVARCHAR if no Unicode needed). Narrow rows = more rows per page = fewer reads. Index keys especially.

28Keep statistics fresh and watch fragmentation

Stale statistics cause bad plans (estimated 1 row, actual 1 million). UPDATE STATISTICS, auto-update on, scheduled index maintenance (rebuild vs reorganise by fragmentation).

29Materialise expensive repeated work

Temp table for intermediate results reused several times, summary tables or indexed views for heavy, stable aggregates, partitioning for huge time-based tables (topics 26, 25, 32). Avoid scalar user-defined functions in WHERE/SELECT on big sets (they run row by row and can block parallelism); prefer inline table-valued functions.

30Read the execution plan, and test with realistic data

Look for scans on big tables, key lookups, spills, and estimate-vs-actual gaps (topic 31). A query that flies on 10 rows can crawl on 10 million: tune against production-sized copies.
