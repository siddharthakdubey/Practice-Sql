Partitions

Split one huge table into smaller pieces by a key such as date. Queries touch only the pieces they need, and old data can be removed in an instant.

After this topic you will explain partitioning, create a partition function, scheme and partitioned table, understand partition elimination and the sliding-window pattern, and know when partitioning helps and when it does not.

The idea

A partitioned table is still one table to your queries, but its rows are stored in several physical partitions, chosen by the value of a partitioning column (usually a date). Think of a filing cabinet with one drawer per month instead of one giant heap of paper.

BenefitHow
Partition eliminationa query on March only reads the March partition; the others are skipped
Fast data loading/removalSWITCH moves a whole partition in or out as a metadata change (milliseconds, no row-by-row delete)
Maintenance per piecerebuild an index or compress only the hot partition
Storage tiersold partitions on cheap disks, current ones on fast SSD (filegroups)
Partitioning is not an index and not automatic speedIt mainly helps very large tables (hundreds of millions of rows, hundreds of GB) and manageability. On a small table it adds complexity for no gain. A good index usually beats partitioning for pure query speed.

The three building blocks (SQL Server)

-- 1. PARTITION FUNCTION: where are the boundaries?
CREATE PARTITION FUNCTION pf_OrderDate (DATE)
AS RANGE RIGHT FOR VALUES ('2025-02-01', '2025-03-01');
--   partition 1: OrderDate < 2025-02-01
--   partition 2: 2025-02-01 <= OrderDate < 2025-03-01
--   partition 3: OrderDate >= 2025-03-01             (RANGE RIGHT: the boundary value belongs to the RIGHT partition)

-- 2. PARTITION SCHEME: where is each partition stored? (filegroups)
CREATE PARTITION SCHEME ps_OrderDate
AS PARTITION pf_OrderDate ALL TO ([PRIMARY]);              -- or a different filegroup per partition

-- 3. TABLE created ON the scheme, naming the partitioning column
CREATE TABLE dbo.OrdersPart (
    OrderID   INT           NOT NULL,
    OrderDate DATE          NOT NULL,
    CustomerID INT          NULL,
    Sales     DECIMAL(10,2) NOT NULL,
    CONSTRAINT pk_OrdersPart PRIMARY KEY CLUSTERED (OrderID, OrderDate)   -- the partition column must be part of unique keys
) ON ps_OrderDate (OrderDate);
  • N boundary values make N+1 partitions. Two boundaries here, three partitions.
  • RANGE LEFT vs RANGE RIGHT decides which side the boundary value goes to. For dates, RIGHT with first-of-month boundaries is the natural choice.
  • The partition column must be part of every unique index (including the primary key). That is a design constraint to plan for.

See the rows land in partitions

INSERT INTO dbo.OrdersPart (OrderID, OrderDate, CustomerID, Sales)
SELECT OrderID, OrderDate, CustomerID, Sales FROM Orders;

SELECT $PARTITION.pf_OrderDate(OrderDate) AS PartitionNo,    -- which partition would this date go to?
       COUNT(*) AS Rows, MIN(OrderDate) AS FromDate, MAX(OrderDate) AS ToDate
FROM dbo.OrdersPart
GROUP BY $PARTITION.pf_OrderDate(OrderDate)
ORDER BY PartitionNo;
PartitionNo | Rows | FromDate | ToDate 1 | 4 | 2025-01-01 | 2025-01-20 2 | 3 | 2025-02-01 | 2025-02-15 3 | 3 | 2025-03-01 | 2025-03-15

Partition elimination

SELECT OrderID, Sales FROM dbo.OrdersPart WHERE OrderDate >= '2025-03-01';

In the actual execution plan, the scan operator shows Actual Partition Count = 1 (of 3). For elimination to work, filter directly on the partition column, sargable (no YEAR(OrderDate) = 2025), and with a matching data type.

The sliding window: add new, drop old

Typical for logs and transactions: keep the last N months online.

-- add next month: split the last (empty) partition
ALTER PARTITION SCHEME ps_OrderDate NEXT USED [PRIMARY];
ALTER PARTITION FUNCTION pf_OrderDate() SPLIT RANGE ('2025-04-01');

-- remove the oldest month instantly: switch it into an identical, empty archive table
ALTER TABLE dbo.OrdersPart SWITCH PARTITION 1 TO dbo.OrdersArchive;     -- metadata only: no rows are copied or logged
-- then merge away the empty boundary
ALTER PARTITION FUNCTION pf_OrderDate() MERGE RANGE ('2025-02-01');

Compare with DELETE FROM Orders WHERE OrderDate < ..., which logs every row and can run for hours on a large table. SWITCH takes milliseconds.

Aligned indexes

Create nonclustered indexes on the same partition scheme (ON ps_OrderDate(OrderDate), which is the default if you omit ON): they are aligned, so SWITCH and per-partition maintenance still work.

Other databases: PostgreSQL has declarative partitioning (PARTITION BY RANGE (OrderDate), one child table per partition), MySQL has PARTITION BY RANGE, Oracle has a full partitioning option. The ideas are the same.

Design checklist

  1. Is the table very large and growing (and typically queried by a date range)? If not, skip it.
  2. Pick a partition column that appears in most queries' filters, with a natural range (date).
  3. Choose granularity (month is common) so partitions are not tiny (thousands of them hurt) nor too big.
  4. Include the column in the clustered/primary key. Keep indexes aligned.
  5. Automate creating future partitions (a scheduled job), or inserts past the last boundary pile into the last partition.
  6. Test with the actual plan for elimination, and keep statistics up to date.
