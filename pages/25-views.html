Views

A view is a saved query that behaves like a table. It stores the definition, not the data.

After this topic you will create, change and drop views, use them to simplify queries and restrict access, know when a view can be updated, and understand indexed (materialised) views.

Create a view

CREATE VIEW dbo.v_DeliveredOrders AS
SELECT OrderID, CustomerID, ProductID, OrderDate, Sales
FROM   Orders
WHERE  OrderStatus = 'Delivered';
GO                                   -- CREATE VIEW must be the only statement in its batch

SELECT * FROM dbo.v_DeliveredOrders WHERE Sales > 30;       -- use it exactly like a table
OrderID | CustomerID | ProductID | OrderDate | Sales 1005 | 4 | 102 | 2025-02-01 | 40 1008 | 1 | 105 | 2025-03-01 | 50 1010 | 4 | 104 | 2025-03-15 | 45
  • Nothing is copied. Every time you query the view, SQL Server substitutes its SELECT into your query and runs the lot against the base tables.
  • So a view is always up to date.

Change and remove

CREATE OR ALTER VIEW dbo.v_DeliveredOrders AS      -- SQL Server 2016 SP1+: create or replace in one step
SELECT OrderID, CustomerID, Sales FROM Orders WHERE OrderStatus = 'Delivered';

ALTER VIEW dbo.v_DeliveredOrders AS ...;            -- older way
DROP VIEW IF EXISTS dbo.v_DeliveredOrders;
EXEC sp_helptext 'dbo.v_DeliveredOrders';           -- show the definition

-- a richer reporting view
CREATE OR ALTER VIEW dbo.v_OrderDetails AS
SELECT o.OrderID, o.OrderDate, c.FirstName AS Customer, c.Country,
       p.Product, p.Category, o.Quantity, o.Sales,
       e.FirstName AS SalesPerson
FROM       Orders    o
LEFT JOIN  Customers c ON c.CustomerID = o.CustomerID
LEFT JOIN  Products  p ON p.ProductID  = o.ProductID
LEFT JOIN  Employees e ON e.EmployeeID = o.SalesPersonID;
GO
SELECT Category, SUM(Sales) FROM dbo.v_OrderDetails GROUP BY Category;   -- simple for the user

Security with a view

CREATE VIEW dbo.v_EmployeePublic AS
SELECT EmployeeID, FirstName, LastName, Department FROM Employees;      -- no Salary, no BirthDate
GO
GRANT SELECT ON dbo.v_EmployeePublic TO hr_readonly;                     -- DCL (topic 2)
DENY  SELECT ON dbo.Employees        TO hr_readonly;

Changing data through a view

A simple view on one table without aggregates, DISTINCT, GROUP BY or TOP can accept INSERT/UPDATE/DELETE: SQL Server passes them to the base table. Views with joins, aggregates or calculated columns are generally read-only (or need INSTEAD OF triggers, topic 29).

UPDATE dbo.v_DeliveredOrders SET Sales = 22 WHERE OrderID = 1001;      -- updates Orders

The "disappearing row" surprise: you can UPDATE through the view in a way that makes the row fall outside the view's WHERE. Prevent it:

CREATE VIEW dbo.v_Delivered AS SELECT OrderID, OrderStatus, Sales FROM Orders WHERE OrderStatus = 'Delivered'
WITH CHECK OPTION;       -- rejects changes that would make a row invisible to the view (e.g. setting the status to 'Shipped')

Views do not make things faster (usually)

  • A normal view is just stored text; the query is as slow as its SELECT. Stacking views on views hides cost and can produce enormous plans. Keep layers shallow.
  • ORDER BY is not allowed in a view (unless TOP/OFFSET), because a table has no order. Sort when you query the view.
  • SELECT * in a view freezes the column list at creation time: columns added later do not appear until you refresh with EXEC sp_refreshview. List columns explicitly.

Indexed (materialised) views

If you put a unique clustered index on a schema-bound view, SQL Server does store its result and keeps it in sync automatically on every change. Reads of heavy aggregates become instant; writes to the base tables get slower.

CREATE VIEW dbo.v_SalesByCustomer WITH SCHEMABINDING AS
SELECT CustomerID, SUM(Sales) AS Total, COUNT_BIG(*) AS Cnt      -- COUNT_BIG(*) is mandatory with GROUP BY
FROM dbo.Orders WHERE CustomerID IS NOT NULL
GROUP BY CustomerID;
GO
CREATE UNIQUE CLUSTERED INDEX ix_v_SalesByCustomer ON dbo.v_SalesByCustomer (CustomerID);
RestrictionsNo outer joins, subqueries, DISTINCT, window functions; SUM of nullable columns needs care. Postgres/Oracle call the stored-result concept a materialized view and refresh it on demand instead.
