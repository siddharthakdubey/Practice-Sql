SQL joins (basics)

Combine columns from two tables by matching rows. INNER, LEFT, RIGHT and FULL, animated row by row.

After this topic you will explain what a join does, choose between INNER/LEFT/RIGHT/FULL, predict the row count, and write multi-table joins with aliases.

Why join?

Good design stores each fact once: customer names in Customers, orders in Orders. The order only keeps the CustomerID (a foreign key). To see "who bought what" you join the tables back together on that key.

Notice the planted problems: Anna (5) has no orders, and order 1004 points to customer 6 who does not exist. They show the difference between join types.

Without a join: the CROSS product (a warning)

SELECT * FROM Customers, Orders;    -- 5 x 10 = 50 rows: every combination. Almost never what you want.

A join is "that product, filtered to the rows where the keys match". The engine does not really build 50 rows, but logically it is the same.

Anatomy of a join

SELECT c.FirstName, o.OrderID, o.Sales
FROM   Customers AS c            -- LEFT table
INNER JOIN Orders AS o           -- RIGHT table
       ON o.CustomerID = c.CustomerID;   -- the join condition
  • Left table = the one written before JOIN. Right table = after.
  • ON says which rows belong together.
  • Give tables short aliases (c, o) and prefix columns with them. Required when a column name exists in both tables (CustomerID), and kind to the reader always.

INNER JOIN: only the matches

Keeps rows only when a match exists on both sides. JOIN alone means INNER JOIN.

Two surprises you just sawCustomers with several orders repeat (Kevin appears 3 times) so a join can have more rows than either table. And rows without a partner (Anna, order 1004) silently vanish.

LEFT JOIN: keep every left row

All rows of the left table, plus matching right rows. No match gives NULLs on the right side.

The classic use: "all customers, including those who never ordered". And the classic follow-up, "only those who never ordered", is a LEFT JOIN with WHERE o.OrderID IS NULL (an anti join, topic 9).

RIGHT JOIN: keep every right row

Mirror image of LEFT. Most people simply swap the table order and use LEFT JOIN, because reading "main table first" is easier.

SELECT c.FirstName, o.OrderID, o.Sales
FROM   Customers c
RIGHT JOIN Orders o ON o.CustomerID = c.CustomerID;
-- identical to:  FROM Orders o LEFT JOIN Customers c ON ...  (columns in another order)

FULL JOIN: keep everything from both sides

Matches combined, plus unmatched rows from both tables with NULLs on the missing side.

Joining more than two tables

Chain joins; each one joins the result so far to a new table.

SELECT c.FirstName, p.Product, o.Quantity, o.Sales, e.FirstName AS SoldBy
FROM       Orders    AS o
LEFT JOIN  Customers AS c ON c.CustomerID   = o.CustomerID
LEFT JOIN  Products  AS p ON p.ProductID    = o.ProductID
LEFT JOIN  Employees AS e ON e.EmployeeID   = o.SalesPersonID;
HabitStart from the "main" table (the one whose rows you want to count), then LEFT JOIN the lookup tables onto it. An INNER JOIN in the middle of a chain of LEFT JOINs silently deletes the unmatched rows again.

Common mistakes

  • Forgetting the ON (or using the wrong columns): you get a huge cross product.
  • Filtering the right table in WHERE after a LEFT JOIN: WHERE o.OrderStatus='Delivered' turns the LEFT JOIN into an INNER JOIN, because NULL rows fail the test. Put the condition in ON instead (see topic 9).
  • Joining on non-unique columns multiplies rows (a "fan-out") and inflates SUMs. Check the row count before and after.
  • Joining on text with different case/spaces/types ('USA' vs 'usa '): clean first.
  • NULL never equals NULL, so rows with NULL keys do not match each other.
