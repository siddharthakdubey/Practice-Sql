Indexes

The book-index of a table: a sorted structure that lets SQL Server jump straight to the rows instead of reading everything.

After this topic you will explain clustered vs nonclustered indexes, B-trees, seek vs scan vs key lookup, design composite and covering indexes, write sargable filters, and weigh the cost of indexes on writes.

The idea

Without an index, to find the orders of customer 3 the engine reads every row (a scan). With an index on CustomerID it jumps to the right place in a sorted list (a seek), like using the index at the back of a book instead of reading every page.

With 10 rows nobody notices. With 100 million rows, the difference is milliseconds against minutes.

How it is stored: the B-tree

SQL Server stores tables and indexes in 8 KB pages. An index is a balanced tree of pages (B-tree):

                 [ Root page ]           1 read     "keys below 4 go left, 4 and above right"
                /             \
        [ Intermediate ]   [ Intermediate ]       1 read each level
           /     \             /     \
     [Leaf]   [Leaf]      [Leaf]   [Leaf]         leaf pages hold the sorted keys (and pointers or the data)

Even a table of a billion rows is typically only 3 to 4 levels deep: a seek reads 3 to 4 pages. A scan reads millions.

Clustered index: the table itself, sorted

  • The leaf level is the data. Rows are physically ordered by the clustering key.
  • Only one per table (data can be in one order).
  • A PRIMARY KEY creates a clustered index by default. A table with no clustered index is a heap (unordered).
  • Good key: narrow, unique, ever-increasing, rarely changed (an IDENTITY int). A random GUID causes page splits and fragmentation.

Nonclustered index: a separate lookup structure

  • Leaf holds the index columns + a pointer to the row (the clustering key, or a row id for a heap).
  • Up to 999 per table, but each one costs space and write time.
  • Finding extra columns not in the index requires a key lookup: one extra seek into the clustered index per row.
CREATE NONCLUSTERED INDEX ix_Orders_CustomerID ON dbo.Orders (CustomerID);
CREATE UNIQUE INDEX      ux_Customers_Name    ON dbo.Customers (FirstName, LastName);   -- also enforces uniqueness
CREATE CLUSTERED INDEX   cx_X ON dbo.SomeHeap (Id);
DROP INDEX ix_Orders_CustomerID ON dbo.Orders;

Which operation does the engine use?

OperationMeaningCost
Clustered Index Scan / Table Scanread the whole tableproportional to table size
Index Seeknavigate the tree to the matching key(s)tiny (levels + matching rows)
Index Scanread all of an index (smaller than the table)middle
Key Lookup (RID lookup)for each seek hit, fetch missing columns from the tablefine for few rows, painful for thousands

A seek is not always better: if you need 40% of the table, scanning is cheaper than 40% of the rows as random lookups. The optimizer decides using statistics on value distribution.

Composite (multi-column) indexes: order matters

CREATE INDEX ix_Orders_Cust_Date ON dbo.Orders (CustomerID, OrderDate);

Like a phone book sorted by last name, then first name. It helps queries that filter on the left-most columns:

Query filterUses the index well?
WHERE CustomerID = 2yes (seek on first column)
WHERE CustomerID = 2 AND OrderDate >= '2025-02-01'yes (seek on both)
WHERE OrderDate >= '2025-02-01'no (second column alone: like finding all "Anna"s in a phone book sorted by surname)
WHERE CustomerID = 2 ORDER BY OrderDateyes, and no sort needed: data already in order

Rule of thumb for column order: equality columns first, then the range/sort column; the most selective (fewest matching rows) first when everything is equality.

Covering indexes and INCLUDE

If every column a query needs is inside the index, no key lookup is needed: the index covers the query.

CREATE INDEX ix_Orders_Cust_Covering
ON dbo.Orders (CustomerID)                 -- key: used for searching / sorting
INCLUDE (OrderDate, Sales);                -- payload: stored in the leaf only, not sorted

SELECT OrderDate, Sales FROM Orders WHERE CustomerID = 3;     -- answered entirely from the index

Sargable: write filters the index can use

Search ARGument able: the engine can seek if the indexed column stands alone on one side of the comparison.

Bad (scan)Good (seek)
WHERE YEAR(OrderDate) = 2025WHERE OrderDate >= '2025-01-01' AND OrderDate < '2026-01-01'
WHERE UPPER(FirstName) = 'KEVIN'WHERE FirstName = 'Kevin' (default collation is case-insensitive)
WHERE Sales * 1.18 > 100WHERE Sales > 100 / 1.18
WHERE FirstName LIKE '%vin'WHERE FirstName LIKE 'Ke%' (leading wildcard kills it)
WHERE CustomerID = '3' (text vs int: implicit conversion)WHERE CustomerID = 3 (same type)
WHERE ISNULL(ShipDate, '1900-01-01') = '1900-01-01'WHERE ShipDate IS NULL

The price of an index

  • Writes slow down: every INSERT/UPDATE/DELETE must also update every index on the table.
  • Storage: each index is another copy of some columns.
  • Maintenance: indexes fragment as data changes. Rebuild or reorganise when it matters: ALTER INDEX ALL ON dbo.Orders REBUILD; (or REORGANIZE), and keep statistics fresh (UPDATE STATISTICS).
BalanceRead-heavy reporting tables like many indexes; write-heavy transaction tables (payments, logs) like few. Index what you filter, join, group and order by: foreign key columns, frequent WHERE columns. Do not index low-selectivity columns alone (a bit flag), tiny tables, or columns that are rarely used. Drop unused and duplicate indexes.

Find what is needed

SELECT * FROM sys.dm_db_missing_index_details;                   -- what the optimizer wished existed
SELECT OBJECT_NAME(object_id) AS t, name, user_seeks, user_scans, user_updates
FROM sys.indexes i JOIN sys.dm_db_index_usage_stats s ON s.object_id = i.object_id AND s.index_id = i.index_id;   -- used vs only maintained

Treat missing-index suggestions as hints, not orders: merge overlapping ones and test them. The execution plan (topic 31) shows what an index really does for your query.

Try it

1) Run SET STATISTICS IO ON; SELECT * FROM Orders WHERE CustomerID = 3; then create ix_Orders_CustomerID and run again. (With 10 rows the optimizer may still scan: the whole table is one page! Load more rows to see the difference, e.g. insert 100 000 generated orders with a recursive CTE or a cross join.) 2) Make the query covered with INCLUDE and watch the key lookup disappear from the plan. 3) Write the sargable version of WHERE MONTH(OrderDate) = 2. 4) Reverse the column order of the composite index and re-test the queries from the table above.
